# AgentShield v1.0 PRD

## 프로젝트 개요

AgentShield는 AI 에이전트의 아웃바운드 네트워크 트래픽을 제어하는 이그레스 방화벽이다.

- GitHub: https://github.com/kamuimk/agentshield
- Language: Rust (edition 2024, MSRV 1.85)
- License: Apache-2.0
- Current: v0.9.0 (344 tests, ~11,900 LOC)

## v1.0 비전

v1.0은 AgentShield를 커뮤니티에 공식 공개하는 첫 릴리스다. 목표는 세 가지:

1. **제로 마찰 시작 경험** — 설치부터 첫 에이전트 실행까지 1분 이내
2. **멀티채널 알림/승인** — Telegram 외에 Slack, Discord 지원으로 접근성 확대
3. **프로덕션 품질** — 커뮤니티에 자신 있게 홍보할 수 있는 안정성과 문서화 수준

## v0.9 현황

### 완료된 기능
- MITM HTTPS inspection + chunked transfer-encoding 지원
- CA 관리 CLI (init, trust, show, export)
- CertCache LRU (per-domain 인증서 동적 생성, max 1000)
- Docker 멀티 플랫폼 이미지 (amd64/arm64)
- Claude Code 네이티브 연동 (`integrate claude-code`)
- 감사 로깅 (request body + DLP findings, DLP 리댁션)
- 로그 검색/필터링 CLI (domain, action, since, until, search)
- 대시보드 (다크/라이트 테마, 타임라인 차트, SSE 실시간)
- 설정 검증 CLI (`validate`)
- Policy hot-reload (file watcher + SIGHUP)
- AskBroadcaster (Terminal + Telegram + Web Dashboard)
- Rate limiting (도메인별 sliding window)
- DLP (15+ 패턴, Critical/High/Medium)
- 환경변수 치환 (TOML 내 `${VAR}`)
- 한국어 문서

### 미비한 점
- 설치가 `git clone && cargo build` 뿐 (바이너리 배포 없음)
- 첫 사용까지 5~6단계 필요 (init → template → edit TOML → ca init → ca trust → start)
- 알림/ASK가 Telegram만 지원
- `wrap` 커맨드 없음 (에이전트 실행 래퍼)
- 테스트가 대부분 유닛 — E2E 통합 테스트 부족
- CI에서 실제 프록시 파이프라인 테스트 없음

## 요구사항

### R1: `agentshield wrap` — 원커맨드 에이전트 실행 [P0]

v1.0의 핵심 DX 기능. CA 설정, 프록시 시작, 환경변수 주입, 에이전트 실행, 종료 시 정리를 **단 한 줄**로 수행한다.

```bash
# Claude Code를 AgentShield 보호 하에 실행
agentshield wrap -- claude

# OpenClaw 실행
agentshield wrap -- npx openclaw

# 커스텀 명령
agentshield wrap -- python my_agent.py

# MITM 모드 명시
agentshield wrap --mitm -- claude
```

#### R1-1: wrap 실행 흐름

1. `agentshield.toml` 확인, 없으면 자동 생성 (기본 정책: default deny + LLM API allow)
2. `--mitm` 플래그 시: CA 인증서 확인, 없으면 자동 생성 (`ca init` 로직 재사용)
3. 프록시 서버를 백그라운드 스레드로 시작
4. 환경변수 세팅:
   - `HTTP_PROXY=http://127.0.0.1:{port}`
   - `HTTPS_PROXY=http://127.0.0.1:{port}`
   - `--mitm` 시: `NODE_EXTRA_CA_CERTS={ca_cert_path}`
5. 자식 프로세스로 `--` 뒤의 명령 실행 (inherit stdio)
6. 자식 프로세스 종료 시: 프록시 graceful shutdown, exit code 전달

#### R1-2: wrap 추가 옵션

```
agentshield wrap [OPTIONS] -- <COMMAND> [ARGS...]

Options:
  --mitm              Enable MITM TLS interception
  --template <name>   Apply policy template (default: auto-detect from command)
  --port <port>       Override proxy port (default: 18080)
  --dashboard         Also start web dashboard
  --verbose           Show AgentShield startup logs
  --config <path>     Custom config file path
```

#### R1-3: 에이전트 자동 감지

`wrap`은 실행 명령어에서 에이전트를 자동 감지하여 적절한 정책 템플릿을 적용한다:

| 명령어 패턴 | 감지 에이전트 | 기본 템플릿 |
|------------|-------------|------------|
| `claude`, `claude-code` | Claude Code | `claude-code-default` |
| `openclaw`, `npx openclaw` | OpenClaw | `openclaw-default` |
| `aider` | Aider | `aider-default` (신규) |
| `codex`, `openai` | OpenAI Codex | `codex-default` (신규) |
| 기타 | Unknown | `strict` (default deny) |

자동 감지를 `--template`으로 오버라이드 가능.

#### R1-4: 구현 참고

- `std::process::Command`로 자식 프로세스 실행, `.env()` 로 환경변수 주입
- 프록시는 같은 프로세스 내 `tokio::spawn`으로 실행 (별도 프로세스 X)
- `Ctrl+C`/`SIGTERM` 시 자식 프로세스에 시그널 전달 + graceful shutdown
- 자식 프로세스의 exit code를 AgentShield의 exit code로 사용

#### R1-5: 테스트

- wrap 없이 프록시 + 자식 프로세스 + 환경변수 주입 단위 테스트
- auto-detect 로직 테스트 (명령어 → 템플릿 매핑)
- 자식 프로세스 종료 시 프록시 shutdown 확인
- `--mitm` 시 CA 자동 생성 확인

### R3: Slack 알림 + Interactive ASK [P0]

#### R3-1: Slack Incoming Webhook (알림)

가장 간단한 방식으로 Slack에 알림을 보낸다. Slack App 설치 없이 Incoming Webhook URL만으로 동작.

```toml
[notification]
enabled = true

[notification.slack]
webhook_url = "${AGENTSHIELD_SLACK_WEBHOOK}"
channel = "#agentshield"    # optional, webhook default 사용 가능
```

알림 포맷: Slack Block Kit 사용 (rich formatting)

```json
{
  "blocks": [
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "🚫 *DENIED* `POST api.openai.com/v1/chat/completions`\n`Rule: no-openai (domain not in allowlist)`"
      }
    }
  ]
}
```

#### R3-2: Slack Interactive ASK (Socket Mode)

Slack Socket Mode를 사용하여 양방향 ASK 승인/거부를 구현한다. Incoming Webhook은 단방향이므로 Socket Mode가 필요.

```toml
[notification.slack]
webhook_url = "${AGENTSHIELD_SLACK_WEBHOOK}"
app_token = "${AGENTSHIELD_SLACK_APP_TOKEN}"     # xapp-... (Socket Mode)
bot_token = "${AGENTSHIELD_SLACK_BOT_TOKEN}"     # xoxb-... (Bot User)
interactive = true
```

ASK 요청 시:
1. Slack에 Allow/Deny 버튼이 포함된 메시지 전송
2. Socket Mode로 버튼 클릭 이벤트 수신
3. `AskBroadcaster`에 응답 전달 (기존 Telegram interactive와 동일 패턴)

`interactive = false`이면 webhook만 사용 (알림 전용, app_token/bot_token 불필요).

#### R3-3: Slack Notifier 구현

기존 `Notifier` trait를 구현:

```rust
pub struct SlackNotifier {
    webhook_url: String,
    channel: Option<String>,
    client: reqwest::Client,
}

#[async_trait]
impl Notifier for SlackNotifier {
    async fn notify(&self, event: &NotificationEvent) -> anyhow::Result<()> {
        let payload = self.format_slack_message(event);
        self.client.post(&self.webhook_url)
            .json(&payload)
            .send()
            .await?;
        Ok(())
    }
}
```

#### R3-4: SlackAskResponder 구현 (interactive mode)

기존 `AskResponder` trait를 구현:

```rust
pub struct SlackAskResponder {
    app_token: String,
    bot_token: String,
    channel: String,
}

#[async_trait]
impl AskResponder for SlackAskResponder {
    async fn send_ask(&self, request: &AskRequest) -> anyhow::Result<()>;
    async fn poll_response(&self) -> anyhow::Result<Option<AskResponse>>;
}
```

Socket Mode 연결: `tungstenite` 또는 `tokio-tungstenite` crate 사용.

#### R3-5: 테스트

- Webhook 알림 포맷 테스트 (각 이벤트 타입별)
- Webhook 전송 실패 시 graceful 처리 (프록시 블로킹 없음)
- Socket Mode 연결/재연결 테스트
- ASK 버튼 클릭 → AskBroadcaster 응답 전달 테스트
- `interactive = false`일 때 Socket Mode 비활성 확인

### R7: E2E 통합 테스트 [P1]

현재 테스트는 대부분 유닛 레벨이다. v1.0에서는 실제 프록시 파이프라인을 검증하는 E2E 테스트를 추가한다.

#### R7-1: 테스트 시나리오

1. **기본 Allow/Deny 흐름**: 프록시 시작 → HTTP 요청 → 정책 평가 → 응답 확인
2. **MITM DLP 스캔**: MITM 모드 프록시 → HTTPS 요청 with API key → DLP deny 확인
3. **Rate Limiting**: 연속 요청 → N+1번째에서 429 확인
4. **ASK 흐름**: ASK 정책 → 터미널 승인 시뮬레이션 → allow 확인
5. **Policy Hot-Reload**: 프록시 실행 중 TOML 변경 → 새 정책 적용 확인
6. **wrap 커맨드**: `wrap -- echo hello` → 프록시 시작 + 환경변수 주입 + 자식 실행 + 종료

#### R7-2: 구현 방식

`tests/e2e/` 디렉토리에 별도 테스트 바이너리. 각 테스트가 실제 프록시를 포트 0으로 시작하고, `reqwest` 클라이언트로 프록시 경유 요청을 보낸다. 외부 서버 의존 없이 로컬 mock 서버(tokio TCP) 사용.

```rust
#[tokio::test]
async fn e2e_deny_blocks_request() {
    let mock = start_mock_server().await;  // 200 OK 반환
    let proxy = start_proxy_with_policy("deny", &mock.addr()).await;
    
    let client = reqwest::Client::builder()
        .proxy(reqwest::Proxy::all(&proxy.url()).unwrap())
        .build().unwrap();
    
    let resp = client.get(mock.url()).send().await.unwrap();
    assert_eq!(resp.status(), 403);
}
```

#### R7-3: CI 통합

E2E 테스트를 CI에서 별도 step으로 실행 (`cargo test --test e2e`). 실패 시 프록시 로그 출력.

### R8: 대시보드 개선 [P2]

#### R8-1: 대시보드를 React SPA로 리팩토링

현재 인라인 HTML인 대시보드를 독립적인 React SPA로 리팩토링한다. 빌드된 정적 파일을 `include_bytes!`로 바이너리에 임베딩.

주요 개선:
- **반응형 레이아웃** — 모바일에서도 사용 가능
- **필터링 UI** — 도메인, 액션, 시간 범위 필터 (CLI와 동일)
- **페이지네이션** — 로그가 많을 때 무한 스크롤
- **정책 편집기 개선** — TOML 시각적 편집 (rule 추가/삭제/재정렬) 또는 TOML 에디터
- **ASK 이력** — 과거 ASK 요청과 응답 이력 조회

#### R8-2: 대시보드 인증 개선

현재 Bearer token 방식에 추가로:
- 초기 비밀번호 설정 UX (quickstart에서 생성)
- 세션 기반 인증 (토큰 입력 → 쿠키/세션 발급)

#### R9-1: 랜딩 페이지

### R10: Graceful Shutdown + 시그널 처리 [P1]

#### R10-1: 현재 문제

`agentshield start`는 Ctrl+C 시 즉시 종료되며, 진행 중인 연결이 끊긴다. `wrap` 모드에서는 자식 프로세스도 함께 종료되어야 한다.

#### R10-2: 구현

- `tokio::signal::ctrl_c()` + `SIGTERM` 핸들링
- 진행 중인 연결에 대해 타임아웃(5초) 후 강제 종료
- `wrap` 모드: 자식 프로세스에 `SIGTERM` 전달 → 자식 종료 대기(10초) → `SIGKILL`
- 종료 시 notification 이벤트 전송 (shutdown)
- DB 연결 풀 정리

### R11: 성능 및 안정성 [P2]

#### R11-1: 연결 타임아웃 설정화

현재 MITM 응답 스트리밍에 30초 하드코딩 타임아웃이 있다. 설정 가능하게 변경:

```toml
[proxy]
listen = "127.0.0.1:18080"
connect_timeout = 10     # upstream 연결 타임아웃 (초)
idle_timeout = 300       # 유휴 연결 타임아웃 (초)
max_body_size = 10485760 # 최대 body 크기 (바이트, 기본 10MB)
```

#### R11-2: 동시 연결 제한

`tokio::sync::Semaphore`로 최대 동시 연결 수 제한 (기본 1024).

```toml
[proxy]
max_connections = 1024
```

#### R11-3: 메트릭 엔드포인트

`/api/metrics`에서 Prometheus-compatible 메트릭 노출:
- `agentshield_requests_total{action="allow|deny|ask"}`
- `agentshield_active_connections`
- `agentshield_request_duration_seconds`
- `agentshield_cert_cache_hits_total`
- `agentshield_cert_cache_misses_total`

## 기술적 설계 노트

### 알림 아키텍처 확장

현재 `Notifier` trait + `AskResponder` trait 구조를 유지하면서 Slack/Discord를 추가:

```
NotificationConfig
├── telegram: Option<TelegramConfig>
├── slack: Option<SlackConfig>        # 신규
└── discord: Option<DiscordConfig>    # 신규

AskBroadcaster
├── Terminal AskResponder (기존)
├── Telegram AskResponder (기존)
├── Web Dashboard AskResponder (기존)
├── Slack AskResponder (신규)         # Socket Mode
└── Discord AskResponder (신규)       # Gateway API
```

### wrap 아키텍처

```
agentshield wrap -- claude
    │
    ├─ [main thread] Parse args, detect agent
    ├─ [tokio runtime] Start proxy server
    ├─ [tokio runtime] Start notification listeners (if configured)
    ├─ [main thread] Set env vars (HTTP_PROXY, HTTPS_PROXY, NODE_EXTRA_CA_CERTS)
    ├─ [main thread] Spawn child process with inherited env
    ├─ [main thread] Wait for child exit OR signal
    └─ [cleanup] Stop proxy, flush logs, exit with child's exit code
```

### 새 Cargo 의존성 (예상)

| Crate | 용도 | 크기 |
|-------|------|------|
| `tokio-tungstenite` | Slack Socket Mode + Discord Gateway | ~50KB |
| `ctrlc` 또는 `signal-hook` | 크로스 플랫폼 시그널 처리 | ~15KB |

`serenity` (Discord 전용) 같은 무거운 프레임워크는 사용하지 않고, REST + WebSocket 직접 구현으로 의존성 최소화.

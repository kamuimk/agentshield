# AI 에이전트의 프롬프트 인젝션 대응 검토

상태: 2026-10-16 조사·제안. 아래 전체 방어가 구현됐다는 뜻이 아니다.

## 보호 목표

웹·문서·저장소·MCP 응답의 악성 지시 때문에 에이전트가 서비스 비밀값을 조회하거나,
허용 범위 밖으로 데이터를 보내거나, 서비스 설정을 변경하는 피해를 제한한다.
문장 탐지기나 모델 하나로 모든 인젝션을 판별할 수 있다고 보장하지 않는다.

확인한 지침은 권한 결정을 모델 밖에서 수행하고, 도구·데이터 접근을 제한하며,
민감 작업을 실제 인자에 묶어 승인하고, 공격 시나리오로 검증하는 방향이다.
이는 통신 프록시에만 맡길 수 없다. WorkOS 실행 계층과 OS 통제의 역할을 구분한다.

## 우선 방어와 적용 위치

| 공격 예시 | 방어 제안 | 적용 위치 |
| --- | --- | --- |
| 문서가 운영 비밀값 조회를 지시 | 현재 작업에 허용된 secret/환경/작업만 승인; 원문은 모델에 미제공 | WorkOS 도구 실행 계층·AWS IAM |
| 읽은 자료를 공격자 서버로 전송 | 실제 목적지·작업·내용 검사와 승인 | 전송 전 게이트·AgentShield·OS |
| 허용된 Slack/GitHub를 반출에 악용 | 도메인 외에 workspace/channel/repository/작업 제한 | WorkOS 공급자 어댑터 |
| 외부 내용이 관리자·승인자로 위장 | 도구 결과·문서를 권한 부여 근거로 사용하지 않음 | WorkOS 실행 계층 |
| 승인 직후 수신자·본문 변경 | 실제 실행 인자/본문 digest·만료·일회성에 승인 결박 | WorkOS 승인 계층 |
| 에이전트가 Slack 승인 버튼을 대신 누름 | 에이전트 주체와 승인자 분리; 독립 인증 경로 사용 | WorkOS·Slack 승인 연결 |
| 저장소의 지시 파일·MCP 설명 변조 | 버전·digest·출처 추적, 도구 계약 변경 시 재검토 | 설치·도구 등록·업데이트 |
| 지시를 장기 메모리에 저장 | 출처·신뢰도·소유자 보존; 보안 정책으로 승격하지 않음 | WorkOS 메모리 계층 |

AWS Secrets Manager는 기존 정본을 유지한다. 로컬의 조회 권한 자체도 악용 가능하므로
GetSecretValue/BatchGetSecretValue에 대한 IAM 범위와 도구 실행 경로를 검토한다.
비밀값이 필요한 작업은 가능하면 실행기가 원문을 사용하고 모델에는 결과만 반환한다.
서버 실행기·권한까지 침해되지 않는다는 전제가 필요하며 로컬 후킹만으로 보장하지 않는다.

외부 입력은 출처가 표시된 자료로 다루되, 라벨·구분자·다른 모델의 판정만으로
허용 여부를 확정하지 않는다. 사용자 작업 범위는 인증된 주체가 실행 전에 정한다.
파일을 읽은 뒤의 정보 흐름 추적은 단순 문맥 태그가 아닌 별도 구현·평가 대상이다.

## 검사기가 맡을 부분

프롬프트 검사기는 역할 사칭·권한 변경 요구·비밀값 반출 지시 같은 신호를 보조 탐지한다.
정규식·분류 모델의 위음성/위양성을 측정하고 우회 가능한 점을 명시한다.
검사에 사용하는 모델은 실행 도구·자격증명·정책 변경 권한이 없어야 한다.
회사 자료를 외부 검사 서비스로 보내는 것은 별도 데이터 처리 범위 확인이 필요하다.

네트워크 검사에서는 실제 전송할 바이트를 확인한다. 부분 스트림을 이미 전송한 뒤
위험을 발견하면 사전 차단이 아니므로, 민감 요청은 전체 크기를 제한해 전송 전에 검사한다.
암호화·임의 인코딩·새로운 비밀값 형식은 현재 정규식 DLP의 한계다.

## 관측과 감사

에이전트 실행 ID, 사용자·서비스·환경, 입력 출처의 식별값, 도구·자산·작업,
정책 판단, 승인 주체, 실행 결과를 연계한다. 프롬프트·응답·비밀값 원문을
기본 저장하지 않는다. 악성으로 확정된 사실과 단순 의심 신호를 분리한다.
특정 문서가 동작 원인이라는 인과관계는 출처 기록만으로 자동 확정할 수 없다.

현재 AgentShield 요청 로그에는 신뢰할 수 있는 에이전트 실행 신원이 없다.
WorkOS에서 인증된 실행 컨텍스트를 연결해야 하며 클라이언트가 임의로 준 ID를 믿지 않는다.

## 검증 시나리오와 완료 조건

1. 저장소 주석·README·도구 응답에 가짜 관리자 지시를 넣어도 비밀값 조회가 거부된다.
2. 허용되지 않은 사이트뿐 아니라 허용된 서비스의 다른 계정·채널로 보내는 요청도 거부된다.
3. 비밀값을 LLM 요청에 포함하는 시도를 검사하고, 탐지할 수 없는 형식을 통과로 숨기지 않는다.
4. Slack 승인 후 대상·내용을 바꾸거나 승인을 재사용하면 실제 실행 전에 거부된다.
5. 정상 코드 읽기·정상 API 사용은 계속 가능해 오탐과 작업 지연을 측정할 수 있다.
6. 외부 문서나 에이전트가 정책 파일·도구 권한·승인자를 변경할 수 없다.

가짜 비밀값과 고정 fixture만 사용한다. 모델이 공격을 거절했는지와 별개로,
모델이 악성 도구 호출을 요청한 경우도 실행 계층이 차단하는지 확인한다.
검사기 통과율과 권한 경계 차단율을 구분해 보고한다.

## 구현 순서

1. 현재 통신 엔진·내장 대시보드의 제한된 첫 구현을 검증한다.
2. WorkOS 기존 보안 트랙에서 도구 권한·승인·자격증명 경계를 확인해 중복을 피한다.
3. 서비스별 작업 권한과 실제 전송 전 검사를 연결한다.
4. 외부 입력 출처·MCP 계약 변경 추적과 인젝션 신호 탐지를 더한다.
5. WorkOS 번들에 OS 확장을 연결하고 직접 통신 우회 방어를 별도로 검증한다.

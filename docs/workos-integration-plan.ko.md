# WorkOS 대시보드 통합 개발 계획

## 목표

AgentShield의 기존 대시보드를 WorkOS 등 호스트 제품 안에서 재사용한다.
엔진·대시보드·API는 AgentShield에 유지하고 호스트는 설치·수명·접속을 관리한다.
이번 개발은 AgentShield 쪽 연결 기능과 호스트 어댑터를 완성한다.
WorkOS 저장소의 메뉴·배포 번들·로그인 권한 연결과 운영 활성화는 별도 통합 단계다.

## 확정된 방향 보충

- WorkOS를 설치하면 AgentShield 엔진과 macOS 보안 확장도 함께 설치하는 방향이다.
  별도 설치 프로그램을 요구하지 않는다. macOS에서 필요한 확장·필터 승인은
  WorkOS 설치/초기 설정 과정에서 요청하고, 미승인 상태를 보호 활성으로 표시하지 않는다.
- OS 통신 통제는 Network Extension 기반으로 검토한다. HTTPS 평문 검사와는
  별도 계층이며, HTTP 프록시 환경변수만으로 기기 전체를 보호했다고 표시하지 않는다.
- WorkOS가 관리하는 요청은 전송 전 검사·승인 경로를 우선한다.
  Slack 승인은 해당 요청의 대상·내용에 묶고, 응답 없음은 차단으로 처리한다.
- 서비스 비밀값은 이미 AWS Secrets Manager에서 관리한다(사용자 확인).
  신규 비밀값 저장소나 이전 프로젝트를 만들지 않는다.
- 우선 통제 대상은 Secrets Manager에서 로컬로 가져온 비밀값의 파일 저장,
  로그·셸 기록 노출, 다른 프로세스 접근, 허용하지 않은 외부 전송이다.
- 로컬 AWS 자격증명에 GetSecretValue/BatchGetSecretValue 권한이 남아 있으면
  비밀값을 다시 조회할 수 있다. IAM 권한과 요청 경로도 함께 평가한다.
  AWS에 조회 권한이 있는 감염 기기까지 로컬 후킹만으로 통제한다고 주장하지 않는다.
- 서버 워크로드의 정상적인 런타임 메모리 사용·승인된 캐시와 개발자 기기의
  무단 영구 복사본을 구분한다. 모든 캐시를 일괄 금지하지 않는다.
- 배포는 기존 GitHub 연계·리뷰·브랜치 보호를 활용한다.
  별도 배포 차단·승인을 기본 기능으로 추가하지 않는다.

## 비밀값 감사 범위

CloudTrail의 Secrets Manager 조회 기록과 WorkOS의 요청·승인 기록을 연계한다.
기록 대상은 주체, 서비스/환경, 조회 작업, 시각, 판단·실행 결과이며 원문 비밀값은 제외한다.
CloudTrail만으로 로컬 저장 여부나 실제 외부 유출까지 입증할 수는 없다.
로컬 감시는 서비스가 지정한 경로·프로세스에 한정하는 후속 기능으로 설계하고,
현재 프록시가 파일 쓰기를 이미 감시한다고 표시하지 않는다.

근거: [AWS Secrets Manager 감사 기록](https://docs.aws.amazon.com/secretsmanager/latest/userguide/cloudtrail_log_entries.html),
[AWS 모범 사례](https://docs.aws.amazon.com/secretsmanager/latest/userguide/best-practices.html).

## 순서와 완료 조건

1. 연결 계약: 프로토콜 버전·권한·엔드포인트를 인증된 manifest로 제공.
2. 서버 경계: 전용 읽기/제어 토큰, 정확한 부모 origin, loopback 바인딩 검증.
3. 내장 대시보드: 별도 주소, 메모리 전용 인증, 헤더 기반 SSE, 호스트 테마 연동.
4. 호스트 어댑터: iframe 생성·연결·타임아웃·오류·해제 처리. 별도 UI 프레임워크 의존 없음.
5. 검증: 읽기 토큰의 쓰기/승인 거부, 인증 누락·잘못된 origin·토큰 거부,
   정책 변경·ASK 승인 실제 결과, SSE 수신·종료, 로그 HTML 주입 방어를 확인.
6. 문서: 설정·호스트 사용 예·보호 한계와 다음 통합 단계 기록.

## 첫 구현 결과

AgentShield 쪽 내장 라우트·권한 분리·인증된 manifest·호스트 브라우저 어댑터를 구현했다.
HTTP/TLS 요청의 공통 프레이밍, MITM 실제 메서드 정책, 목적지 검증과 DNS 주소 고정,
사설망/메타데이터/CONNECT 포트 제한, 크기·동시 연결·시간 제한도 보강했다.
구체적인 호환성 제한은 [사용 안내](dashboard-integration.md)를 따른다.

검증은 합성 fixture와 로컬 테스트에 한정했다. WorkOS 실제 화면·번들 설치,
OS 시스템 확장, AWS IAM/CloudTrail 연결과 프롬프트 인젝션 방어 전체의
구현·배포·실서비스 E2E는 완료하지 않았다.

인젝션 대응 조사와 후속 검증 시나리오는 [에이전트 방어 검토](agent-injection-defense.ko.md)에 있다.

## 보안 결정

- 기존 관리자 토큰과 구분되는 긴 난수 토큰을 호스트의 안전한 보관소에서 공급한다.
- 내장 화면은 토큰을 URL·local/sessionStorage·postMessage 응답에 넣지 않는다.
- 부모는 iframe의 origin과 window를 확인하고, 자식도 부모 origin과 window를 확인한다.
- CORS를 전체 허용하지 않는다. API 호출은 iframe 내부의 같은 origin에서 수행한다.
- 읽기 권한은 통계·요청 메타데이터·정책 조회만 허용한다. 감사 본문과 ASK payload는 제외한다.
- 제어 권한은 정책 변경과 ASK 결정을 추가로 허용한다. 서비스별 원격 권한을 의미하지 않는다.
- 허용된 호스트의 침해·로컬 관리자 침해를 이 플러그인 계약만으로 방어한다고 주장하지 않는다.
- 새 토큰 설정은 재시작으로 적용한다. 이미 열린 스트림 회수·토큰 TTL은 후속 서버 세션 설계 대상이다.

## 후속 WorkOS 통합

WorkOS의 기존 보안 트랙·담당자와 최신 dev 구현을 확인한 뒤 전용 worktree에서 진행한다.
호스트 어댑터를 WorkOS의 서비스 보호 화면에 연결하고,
native 보관소의 토큰 전달·AgentShield 프로세스 감독·업데이트·포트 소유 검증을 추가한다.
개발/운영 기기와 환경의 권한 매핑 및 실제 서비스 접근 통제는 별도 설계·검증이 필요하다.
엔진이 꺼져도 서버 권한 제한이 유지되는지는 그 통합 단계에서 검증한다.

# AgentShield 서비스 자산 보호 설계

상태: 제안 설계. 아래 기능은 현재 구현되거나 배포된 기능이 아니다.
작성일: 2026-10-16

## 최신 사용자 지시와 현재 개발 범위

아래 초기 설계에서 우선하는 조건은 다음과 같다.

- 서비스 비밀값의 정본은 이미 AWS Secrets Manager다. 별도 저장소 이전을 하지 않는다.
  로컬 영구 복사본·조회 권한·외부 전송을 통제하는 방향으로 구체화한다.
- 배포는 GitHub 연계 경로와 기존 권한 체계를 활용하며 별도 배포 승인 기능을 추가하지 않는다.
- WorkOS 설치 시 엔진·OS 보안 구성요소를 함께 배포하는 것이 목표다.
  OS 확장 활성화 승인은 별도 필요하며, 아직 해당 번들·확장은 구현하지 않았다.
- 현재 첫 개발 범위는 통신 엔진 보강과 AgentShield 대시보드 내장 계약이다.
  뒤의 GitHub 요청 중개는 초기 후보 설계이며 확정된 첫 구현 대상이 아니다.
- AI 에이전트의 프롬프트 인젝션 방어는 [검토 문서](agent-injection-defense.ko.md)를 따른다.
  모델 판정과 별도로 권한·도구 실행·전송 경계를 두는 후속 구현이 필요하다.

진행 계획은 [통합 계획](workos-integration-plan.ko.md), 구현된 연결 방법과
현재 엔진의 보호 범위는 [사용 안내](dashboard-integration.md)에 기록한다.

## 배포 방향 보충: WorkOS 통합

사용자 지시: 별도 프로그램을 여러 개 설치하게 하지 않고 WorkOS와 연동할 수 있다.
이에 따라 별도 AgentShield 앱·상주 데몬·로그인 화면을 추가하는 대신,
WorkOS 데스크톱 배포와 기존 서버 접근 경로를 확장하는 방향을 우선한다.
아래 GitHub 게이트웨이 제안도 새 독립 제품을 만들기보다 기존 경계에 연결한다.

공개 저장소에는 호스트 제품과 연결하는 데 필요한 계약만 기록한다.
호스트 내부의 소스 경로, 결정 문서 식별자, 인증·자격증명 구현은 공개하지 않는다.

| 연동 영역 | 공개 계약의 요구사항 |
| --- | --- |
| 설치·업데이트 | 호스트가 엔진 수명과 버전을 관리하고 실제 보호 상태를 표시한다. |
| 요청 승인 | 인증된 요청 주체와 대상·본문·만료에 결박된 일회성 결정을 전달한다. |
| 자격증명 | 실제 값과 보관 구현을 공개 어댑터에 포함하지 않는다. |
| 감사 | 비밀값 원문 없이 요청 식별값·정책·결정·실행 결과를 연결한다. |
| 접근 회수 | 연결 종료·기기 회수 시 미소비 승인의 사용을 거부한다. |

호스트 측 구현과 실제 배포·검증 자료는 해당 제품의 비공개 저장소에서 관리한다.

### 사용자 경험

- WorkOS 설치·로그인 뒤 권한 있는 서비스와 환경을 선택한다.
- 도구·에이전트는 WorkOS의 허용된 작업 경로로 요청한다.
- 필요한 작업 승인과 접근 상태는 WorkOS 안에서 제공한다.
- 사고 시 WorkOS 세션·기기 접근과 서비스 권한의 회수를 연계한다.
- WorkOS 밖에서 실행한 일반 셸까지 자동 보호된다고 표시하지 않는다.

### 구현 경계

AgentShield의 공개 저장소에는 재사용 가능한 보안 엔진, 대시보드,
WorkOS를 포함한 호스트용 연결 어댑터·API 규격과 합성 테스트를 둘 수 있다.
WorkOS의 온톨로지, 업무 로직, 인증·권한 처리, DB 구조, 운영 설정과
자격증명 구현은 WorkOS의 비공개 저장소에서만 관리한다.

단일 설치는 배포 방식이며 원격 권한 경계를 대신하지 않는다.
호스트의 기존 권한·승인 계약을 유지하면서 공개 연동 계약에 연결해야 한다.
실제 자격증명 보관 방식이나 보호 활성 여부는 공개 문서의 설계만으로 추정하지 않는다.

공개 범위 검토는 코드뿐 아니라 문서, 테스트, 예제, 커밋 메시지와 빌드 산출물에
동일하게 적용한다. 실제 계정·기기·서비스 설정 대신 합성 fixture를 사용한다.
이 문서의 정리가 기존 Git 이력이나 이미 내려받은 복사본까지 제거하지는 않는다.

## 목적과 성공 기준

개발자 기기 또는 AI 에이전트가 침해돼도 운영 서비스의 데이터, 권한,
비밀값, 배포 경로로 피해가 번지는 범위를 제한한다.
개인 데이터 전반을 보호하는 백신이나 범용 EDR을 첫 목표로 삼지 않는다.
개인 계정·브라우저 세션도 서비스 접근 권한을 가진 경우에는 보호 대상이다.

성공 기준은 악성 프로세스 탐지 건수가 아니라 다음 공격의 차단 여부다.

- 로컬 파일·환경변수를 복사해도 서비스의 장기 자격증명을 얻지 못한다.
- 허용된 저장소 읽기 요청으로 다른 저장소 접근이나 쓰기를 수행할 수 없다.
- 개발 권한으로 운영 데이터 조회·변경 또는 배포를 수행할 수 없다.
- 기기 접근을 회수하면 신규 요청이 중단되고, 이미 발급한 권한의 잔존 시간을 설명할 수 있다.
- 로컬 프로그램·정책·로그가 변조돼도 원격 서비스의 권한 제한은 유지된다.

허용된 작업의 악용까지 자동으로 판별한다고 보장하지 않는다.
예를 들어 정상적으로 읽을 수 있는 소스는 해당 기기의 악성코드도 읽을 수 있다.
소스 자체를 기기에 노출하지 않아야 하는 자산에는 원격 개발 환경이 필요하다.

## 사고에서 가져올 위협 모델

제공된 사고 자료에는 원격 스크립트 실행, 관리자 권한 상주 항목,
로컬 브라우저 프로필 수집 흔적이 있다. 외부 업로드 기록은 확보되지 않았다.
정확한 악성코드 계열 판정이나 특정 도메인 탐지에 보호 효과를 의존하지 않는다.

공격자는 로컬 사용자 권한을 가지며, 관리자 권한까지 획득할 수 있다고 가정한다.
프록시 환경변수를 제거하고, 로컬 CLI를 변조하고, 사용자 세션을 이용하고,
정상 API에 직접 접속하고, 이미 허용된 요청을 반복할 수 있다.
클라이언트가 전송한 PID·프로세스 이름·서비스 이름은 신뢰할 신원 증명이 아니다.

원격 게이트웨이와 공급자 측 IAM·저장소 설정·배포 보호 규칙은 별도 신뢰 경계다.
기존 장기 키, 광범위한 SSO 역할, 관리자 웹 세션이 우회 경로로 남아 있으면
게이트웨이를 설치해도 서비스 보호가 완성되지 않는다.

## 보호 자산

| 자산 | 제한 단위 | 별도 대응이 필요한 통로 |
| --- | --- | --- |
| 소스·저장소 | 서비스, 저장소 ID, 작업 | 개인 PAT, SSH 키, GitHub 웹 세션 |
| 클라우드 | 계정, 역할, 리소스, 작업 | 장기 키, SSO 역할, 관리 콘솔 |
| 운영 DB·파일 | 환경, 데이터 범위, 작업, 반출량 | 직접 DB 계정, 백업·스토리지 URL |
| 서비스 비밀값 | 서비스, 용도, 실행 주체 | 로컬 .env, 키체인, CI 로그 |
| 배포 | 저장소, 환경, 아티팩트 식별값, 작업 | CI 토큰, workflow 수정, 배포 관리자 |

실제 서비스명·계정 ID·리소스 목록은 배포별 비공개 설정으로 관리한다.
이 문서에서 특정 서비스의 현재 인프라 구성을 가정하지 않는다.

## 구성과 신뢰 경계

1. 로컬 CLI: 서비스 선택, 접근 요청, 진단, 기존 HTTP 프록시 제공.
2. 원격 접근 게이트웨이: 인증, 자산 정책, 승인 검증, 공급자 요청 중개, 접근 회수.
3. 공급자 어댑터: GitHub·클라우드·DB별로 허용된 작업을 명시적으로 구현.
4. 독립된 감사 저장소: 원격 결정과 실행 결과를 보관.
5. 선택적 원격 작업 환경: 로컬에 데이터나 재사용 가능한 권한을 제공할 수 없는 작업 실행.

원격 게이트웨이는 로컬 프록시를 외부에 공개하는 방식으로 만들지 않는다.
임의 URL·CONNECT·셸 실행을 받는 범용 프록시도 제공하지 않는다.
인증된 주체의 요청을 서버 측 자산 설정에 매핑하고, 공급자·리소스·작업을 제한한다.

서버는 클라이언트가 제출한 서비스 이름만으로 접근을 승인하지 않는다.
사용자 권한, 등록된 클라이언트, 환경, 자산 ID, 작업을 함께 평가한다.
기기 인증도 해당 기기에서 허용 작업을 악용하는 공격을 없애지는 못한다.

## 권한과 승인

기본 결정은 deny다. 개발·스테이징·운영을 서로 다른 자산 범위로 취급한다.
단순 GET 여부가 아니라 실제 작업의 의미로 읽기·쓰기·관리·배포를 구분한다.
GraphQL POST 안에는 읽기와 쓰기가 모두 있으므로 초기에는 허용하지 않는다.

정책 판단 입력에는 인증 주체, 클라이언트 ID, 서비스, 환경, 자산 ID,
작업, 요청 식별값, 정책 버전이 들어간다. 경로·query·본문은 어댑터가 검증한다.
허용되지 않은 입력·알 수 없는 작업은 차단한다.

승인은 요청 내용, 대상, 환경, 만료 시각에 묶인 일회성 결정이다.
대상을 바꾸거나 재전송하면 기존 승인으로 실행할 수 없어야 한다.
민감한 운영 승인은 요청 기기와 분리된 인증 경로를 사용한다.
같은 감염 기기의 터미널에서 허용을 누르는 것만으로 독립 승인을 주장하지 않는다.

자격증명은 서버에 보관하고 가능하면 서버가 요청을 대신 수행한다.
도구 호환성 때문에 단기 권한을 클라이언트에 발급하는 경우에는 훔칠 수 있다고 가정하며,
권한 범위·수명·재사용 가능성·회수 한계를 명시한다.
토큰을 짧게 발급해도 발급 API가 광범위하면 장기적인 악용이 가능하다.

## 기존 코드 활용과 변경

| 현재 코드 | 활용 | 변경 필요 |
| --- | --- | --- |
| src/policy | 기존 로컬 정책 호환 | 서비스·환경·자산·작업 정책 모델 추가 |
| src/proxy | 기존 에이전트 통신 제어 | 강제 보호와 프록시 경유 보호를 구분 |
| src/ask | 알림·승인 UI 어댑터 | 서버의 인증된 일회성 승인으로 연결 |
| src/logging | 로컬 진단 | 원격 감사와 요청·결정·실행 결과 연계 |
| src/web | 로컬 상태 표시 | 원격 관리 API와 인증·인가 경계 분리 |
| src/dlp | 알려진 비밀값 반출의 보조 탐지 | 서비스 접근 통제를 대체하지 않음 |

현재 정책은 도메인·메서드 중심이고 RequestInfo.path는 규칙 매칭에 사용하지 않는다.
현재 ASK는 요청 ID와 bool 응답 중심이며 승인자 권한·승인 범위·정책 버전 모델이 없다.
현재 SQLite는 감염 기기에서 변조 가능한 로컬 기록이다.
현재 웹 API 인증은 선택 사항이므로 그대로 원격 관리 서비스에 사용하지 않는다.

기존 네트워크 기능도 별도 보강한다.

- MITM 복호화 후 실제 HTTP 메서드·대상에 정책을 재평가한다.
- 일반 HTTP의 분할 본문 등 메시지 경계를 완전히 처리한다.
- 파싱 실패·본문 제한 초과 시 검사하지 않은 데이터를 전달하지 않는다.
- 보안상 명시 차단과 운영 알림용 예외를 분리한다.

위 사항은 정적 코드 검토 결과다. 수정 전 공격 재현 테스트로 동작을 확정한다.

## 후속 접근 통제 후보: GitHub 저장소 읽기 게이트웨이

구현 순서는 서비스·환경·자산·작업 정책 모델과 검증 테스트를 먼저 만들고,
한 공급자의 요청 중개로 신뢰 경계를 검증한다. 첫 후보는 GitHub다.
AWS·DB·배포·Mac 실행 차단을 동시에 구현하지 않는다.

제안하는 초기 동작:

- 서버에 설치된 GitHub App으로 명시 등록된 저장소의 필요한 읽기 권한만 사용한다.
- 클라이언트에 App 개인키·설치 토큰을 반환하지 않는다.
- 저장소 메타데이터·등록된 저장소의 파일 읽기 등 작은 작업 집합부터 제공한다.
- 임의 REST 경로, GraphQL, Git push, 관리자 API, 임의 URL 요청은 거부한다.
- 토큰을 전달받거나 임의 업스트림 헤더를 지정하는 입력을 제공하지 않는다.
- 응답 크기·요청량·작업 시간을 제한하고, 리다이렉트는 초기에는 거부한다.
- 서버에서 매 요청 권한을 확인하고 클라이언트 비활성화 후 신규 요청을 거부한다.
- 초기 버전에서는 완전한 git clone 호환이나 이미 받은 데이터의 회수를 보장하지 않는다.

설치 권한 변경, 직접 PAT·SSH 접근 제거 등 공급자 측 설정이 검증돼야
실제 보호 상태로 판정한다. 코드 구현·로컬 테스트·게이트웨이 배포·공급자 설정·
실서비스 경로 검증은 서로 다른 완료 상태로 기록한다.

## 이후 단계

1. GitHub 중개를 가짜 업스트림에서 검증한 뒤 최소 권한 테스트 저장소로 검증.
2. 공급자 측 직접 접근 목록을 진단하고, 운영 접근의 실제 우회 경로를 정리.
3. 클라우드의 제한된 작업 중개 또는 역할 발급을 구현하고 잔존 권한 시간을 검증.
4. 운영 DB 조회와 데이터 반출량 제어를 별도 어댑터로 구현.
5. 배포는 검증된 아티팩트·대상 환경·승인에 묶고 CI 보호 규칙과 연계.
6. 필요하면 Mac 호스트 감시와 원격 개발 환경 연동을 추가.

정책 배포·공급자 설정 변경·기존 키 폐기는 실제 대상과 권한을 확인한 별도 작업이다.
프로젝트 분석 자체를 운영 자격증명 변경이나 접근 차단의 실행 권한으로 취급하지 않는다.

## 필수 검증 시나리오

| 공격·실패 상황 | 기대 결과 |
| --- | --- |
| 로컬 프록시 제거·로컬 설정 변조 | 게이트웨이 정책 유지; 공급자 직접 접근도 별도로 거부됨 |
| 서비스명·저장소 ID 바꿔 요청 | 인증 주체의 허용 범위 밖이면 거부 |
| 읽기 권한으로 쓰기·관리·GraphQL 요청 | 업스트림 실행 전 거부 |
| 경로 인코딩·헤더·리다이렉트로 대상 변경 | 어댑터 검증에서 거부 |
| 승인 뒤 본문·환경·대상 변경 또는 재전송 | 승인 불일치·재사용으로 거부 |
| 접근 회수 후 새 요청 | 거부; 이미 진행 중인 요청과 권한의 잔존 시간은 별도 표기 |
| 게이트웨이·정책 저장소 장애 | 직접 연결·과거 권한으로 자동 우회하지 않음 |
| 로그 수집 | 비밀값·Authorization·쿠키·소스 본문을 기본 저장하지 않음 |
| 로컬 관리자 권한 탈취 | 로컬 진단은 신뢰하지 않아도 원격 정책·감사는 유지 |

가짜 업스트림에서 거부된 요청이 실제로 도달하지 않았는지 검증한다.
권한 회수·승인 일회성·자산 경계는 결과 코드뿐 아니라 실행 여부로 확인한다.
서버 감사에는 요청 ID, 인증 주체, 자산, 작업, 정책 버전, 결정, 실행 결과를 남긴다.
감사 기록에 실패하면 민감 작업은 실행하지 않도록 설계한다.

## 오픈소스와 증거 관리

정책 모델·게이트웨이·어댑터·합성 테스트 샘플은 공개 가능한 구현으로 둔다.
실제 사고 ZIP, 개인 경로, 브라우저 자료, 계정·서비스 식별값, 비밀값은 포함하지 않는다.
실제 서비스 배포 정보는 비공개 설정으로 주입한다.
악성코드 샘플 실행이나 알려진 악성 도메인 접속 없이 합성 시나리오로 검증한다.

## 확인 근거와 남은 결정

기준 코드: d90bc66. 현재 저장소의 src/policy, src/proxy, src/cli/wrap.rs,
src/ask, src/logging, src/web를 정적으로 검토했다.
기존 테스트는 오프라인 실행 시 axum 의존성 캐시 부재로 시작하지 못했다.
빌드·테스트 통과 또는 현재 서비스 보호 효과를 확인했다는 의미가 아니다.

구현 전 확인할 배포별 정보:

- 우선 보호할 서비스와 그 서비스의 GitHub·클라우드·DB·배포 자산 목록.
- 로컬 도구에 반드시 필요한 작업과 로컬로 반환해도 되는 데이터 범위.
- 게이트웨이 운영 위치, 사용자 인증 제공자, 승인자, 감사 보존 요구.
- 기존 장기 키·웹 세션·SSO·SSH의 직접 접근을 줄일 수 있는 범위.
